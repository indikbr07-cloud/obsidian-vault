# Анализ R-Keeper и проектирование локальной системы для кафе

> Цель: разобрать систему автоматизации [r_keeper](https://rkeeper.ru/) и понять, как реализовать аналог локально для 1–2 заведений общепита (кафе).

## 1. Что такое R-Keeper

**R-Keeper** (бренд компании UCS, существует с 1992 года) — комплексная система автоматизации заведений общественного питания. Используется в более чем 70 000 ресторанов в 53 странах. По сути это *экосистема модулей*, где каждый отвечает за свой контур:

- касса/зал
- кухня
- склад и закупки
- бухгалтерия
- лояльность и маркетинг
- доставка и онлайн-заказ
- отчётность и BI

Архитектурно — классическое модульное клиент-серверное решение. Front-office (POS-станции) работают на x86, исторически на Windows (DOS-версия в самых ранних релизах), серверная часть — Microsoft SQL Server, есть веб-надстройки. Linux поддерживается через Wine.

## 2. Состав экосистемы (ключевые модули)

| Модуль | Назначение |
|---|---|
| **Кассовый сервер + Cashier** | Приём заказов, оплата, фискализация, чеки |
| **Manager / r_k WebManager** | Справочники: меню, схемы зала, цены, скидки, права |
| **StoreHouse 5 / Pro** | Складской учёт, ТТК (технико-технологические карты), накладные, себестоимость, инвентаризация |
| **r_keeper Waiter** | Мобильное приложение официанта (приём заказа у стола) |
| **r_keeper KDS** | Kitchen Display System — экраны на кухне |
| **r_keeper Delivery** | Доставка, интеграция с агрегаторами |
| **r_keeper Loyalty** | Дисконт/бонусы/акции/подарочные карты |
| **ПДС (Персональная дисконтная система)** | CRM-подобная карточная программа |
| **WebMonitoring / отчётность** | Онлайн-аналитика, отчёты по выручке, чекам, блюдам |
| **Интеграции** | Бухгалтерия, фискальные принтеры, эквайринг, агрегаторы |

### Принципы, на которых стоит R-Keeper

1. **Справочники как ядро.** Меню, модификаторы, ТТК, налоги, валюты, скидки — единая БД, остальное цепляется к ней.
2. **Заказ как конечный автомат.** Открыт → позиции добавлены → отправлен на кухню → распечатан pre-bill → оплачен → закрыт. Каждый переход логируется.
3. **Раздельные станции, единый сервер.** Несколько касс, KDS, бар-станция — все цепляются к локальному серверу заведения.
4. **Списания привязаны к продажам.** Продал «Цезарь» — StoreHouse автоматически списал ингредиенты по ТТК. Это даёт фудкост и контроль воровства.
5. **Роли и права на каждое действие.** Удаление позиции, скидка, возврат — только с авторизацией менеджера.

> **Важно:** проектируем систему **без привязки к российской нормативке** (54-ФЗ, ЕГАИС, «Меркурий», ОФД, «Честный знак»). Это убирает целый слой обязательной интеграции и сильно упрощает MVP. Если когда-нибудь понадобится — добавится отдельным плагином.

## 3. Что реально нужно для 1–2 кафе

Для одного-двух кафе **не нужна вся махина R-Keeper**. Она оптимизирована для сетей и сложных банкетных холлов. Минимальный полезный набор:

### MVP (must-have)
- Приём заказа на POS / планшете официанта
- Меню с категориями, модификаторами, стоп-листами
- Печать на кухню и бар (роутинг блюд по принтерам/станциям)
- Pre-bill, оплата (наличные/карта/смешанная), разделение счёта
- Печать товарного чека для гостя на ESC/POS-принтере (без фискализации)
- Закрытие смены: X/Z-отчёт по выручке (внутренний, не фискальный)
- Учёт остатков по ТТК (хотя бы простые рецепты «1 блюдо = N ингредиентов»)
- Журнал операций и базовые отчёты: выручка, средний чек, продажи по позициям, по часам

### Should-have
- Управление столами / зоны зала
- Простая дисконтная программа (скидка по карте/телефону)
- Учёт рабочего времени персонала, чаевые, табели
- Инвентаризация и приёмка накладных
- Бэкап БД и история изменений

### Nice-to-have
- KDS на кухне (Android-планшет за 10–15 тыс. ₽)
- Интеграция с агрегаторами доставки (Яндекс.Еда, Delivery Club через их API)
- Отдельный QR-меню с самозаказом со столика
- Telegram-бот для отчёта владельцу в конце смены

### Что **не** нужно сразу делать
- Распределённую репликацию между заведениями (для 1–2 кафе хватит ночной выгрузки в общую БД/Google Sheets/Metabase)
- Сложные ТТК с полуфабрикатами 3-го уровня
- Любые государственные интеграции (фискализация, маркировка, ВСД) — система проектируется как чисто учётная

│                  │                                   │

│           │ - PostgreSQL │                           │

│           │ - агент      │                           │
│           │   ремоут     │                           │

         │ - агрегация 2 кафе       │
         │ - отчёты владельца       │

**Ключевая идея:** сервер живёт **в самом заведении**. Если интернет упал — кафе продолжает работать. Облако нужно только для агрегации и отчётности.

## 5. Технологический стек (рекомендация)

| Слой | Что выбрать | Почему |
|---|---|---|
| **БД** | PostgreSQL 16 | Бесплатно, надёжно, JSONB для меню, отлично переносит частые транзакции |
| **Backend** | Python (FastAPI) | Лучшая экосистема для ИИ (Anthropic SDK, OpenAI SDK, langchain, OCR-библиотеки), типизация через Pydantic |
| **AI Gateway** | Отдельный сервис на Python | Изолирует все вызовы LLM/Vision, кэш, fallback между моделями |
| **Очереди / события** | Redis Streams или NATS | Для отправки заказов на кухню, KDS, KKM |
| **Frontend POS** | React + Vite, или Tauri-приложение | Можно крутить как PWA на любом тач-планшете |
| **KDS** | Та же React-страница, открытая в режиме киоска | Отдельное приложение писать необязательно |
| **Мобильный официант** | PWA (тот же React) | Не нужен Apple Developer аккаунт |
| **Чековый принтер** | python-escpos / node-thermal-printer | Любые ESC/POS термопринтеры (Epson, Star, Xprinter) — без фискалок |
| **Эквайринг** | SDK банка-эквайера (любая страна) | Опционально, можно начать с ручного ввода факта оплаты |
| **Бэкапы** | `pg_dump` + restic в S3 | Восстанавливается за минуты |
| **Мониторинг и сервис** | Prometheus + Grafana + Sentry + remote-агент | См. раздел 7 — сервисное обслуживание |
| **Удалённый доступ** | Tailscale / WireGuard / Cloudflare Tunnel | Безопасный SSH к серверу заведения для саппорта |

### Структура БД (минимальная, накидаю основные таблицы)

- `users` — пользователи (официанты, менеджеры, кассиры) с ролями
- `categories`, `menu_items` — меню
- `modifiers`, `menu_item_modifiers` — модификаторы (без сахара, +сыр)
- `recipes`, `recipe_items` — ТТК (блюдо → N ингредиентов)
- `ingredients`, `stock_movements` — склад и движения
- `tables`, `halls` — столы/зоны
- `orders`, `order_items`, `order_payments` — заказы и оплаты
- `shifts` — смены кассиров
- `discounts`, `loyalty_cards` — скидки/карты
- `audit_log` — журнал действий (кто удалил позицию и т.д.)
- `service_tickets`, `system_health`, `update_versions` — для модуля сервисного обслуживания (см. раздел 7)

**Важно:** `orders` и `order_items` лучше делать как append-only с историей через `order_item_events` — это даёт честный аудит.

## 6. Открытые альтернативы (можно взять за основу или вдохновиться)

Не обязательно писать с нуля — есть рабочие open-source POS:

- **[Floreant POS](https://floreant.org/)** — Java, для малого/среднего ресторана, ставится за минуты, оффлайн
- **Chromis POS** — форк Unicenta, многоязычный, тач-интерфейс
- **SambaPOS** — .NET, очень популярен в Турции, продвинутая система акций
- **UniCenta oPOS** — Java, веб-репортинг
- **Odoo POS** — модуль ERP Odoo, плюс готовый склад/CRM/бухгалтерия

**Как использовать:**
1. **Взять Floreant/SambaPOS как готовый POS** и дописать только то, чего нет (ТТК, агрегаторы, AI-фичи).
2. **Использовать Odoo Community** — закроет POS + склад + лояльность одной системой. Минус: тяжеловат, кастомизация требует Python+XML.
3. **Писать с нуля** — оправдано, только если хочется собственный продукт «на продажу» или специфичные интеграции.

Для 1–2 кафе **самый прагматичный путь** — Odoo Community или Floreant + локальные доработки.

## 7. Сервисное обслуживание системы

Это критичный модуль для самописного решения. R-Keeper держится на сети дилеров; у вашей системы такой сети нет, поэтому нужен **встроенный сервис-слой**, чтобы один человек мог обслуживать оба заведения удалённо.

### 7.1. Что входит в «сервисное обслуживание»

1. **Удалённый доступ** к серверу заведения через зашифрованный туннель (Tailscale / WireGuard / Cloudflare Tunnel). Без проброса портов и публичного IP.
2. **Мониторинг здоровья** в реальном времени:
   - живы ли POS-станции, принтеры, KDS
   - свободное место на диске, температура, состояние БД
   - последний бэкап и его статус
   - падение сервисов → автоматический алерт в Telegram/email
3. **Удалённые обновления** одной кнопкой: `apt`-подобный механизм для всех модулей. Откат на предыдущую версию, если что-то пошло не так.
4. **Тикет-система** для персонала кафе: «Не печатает чек на баре» → создаётся тикет, попадает в админку → саппорт видит, заходит удалённо, чинит.
5. **Лог-центр.** Все логи со всех точек — в одно место (Loki/Grafana или просто `journald` + центральный сборщик), чтобы не лазить по серверам.
6. **Обучающий режим / sandbox.** Копия БД в read-only для обучения нового персонала без риска испортить продакшн.
7. **Чек-листы для админа.** «Утренний прогон»: проверь принтеры, бэкап, KDS, обнови меню — список выводится прямо в админке.

### 7.2. Сервисное обслуживание оборудования кафе (опция)

Можно расширить тот же модуль до учёта **техники и инвентаря** заведения:

- Реестр оборудования: холодильники, печи, кофемашины, посудомойки — с серийниками и датой покупки
- Графики ТО: «кофемашина — чистка раз в неделю, декальцинация раз в месяц, ТО мастером раз в год»
- Журнал инцидентов: «холодильник на кухне №2 течёт с 03.04, мастер придёт 05.04»
- Учёт расходников и запчастей
- Гарантии и контакты сервисных компаний
- Напоминания в Telegram владельцу/шефу

LLM здесь полезна: фото неисправности → vision-модель пытается классифицировать, предлагает базовые шаги диагностики и подбирает инструкцию.

### 7.3. Архитектура сервисного слоя

```
┌──────────────────────────────────────┐
│ Cloud Service Portal                 │
│                                      │
│ - дашборд по всем точкам             │
│ - список тикетов                     │
│ - кнопка «открыть терминал»          │
│ - история обновлений                 │
│ - алерты                             │
└──────────────┬───────────────────────┘
               │
       ┌───────┴─────────┐
       ▼                 ▼
┌──────────────┐   ┌──────────────┐
│ Кафе №1      │   │ Кафе №2      │
│ ┌──────────┐ │   │ ┌──────────┐ │
│ │ remote-  │ │   │ │ remote-  │ │
│ │ agent    │ │   │ │ agent    │ │
│ │ (демон)  │ │   │ │ (демон)  │ │
│ └──────────┘ │   │ └──────────┘ │
│ - heartbeat  │   │ - heartbeat  │
│ - метрики    │   │ - метрики    │
│ - логи       │   │ - логи       │
│ - туннель    │   │ - туннель    │
└──────────────┘   └──────────────┘
```

**`remote-agent`** — маленький Python/Go-демон на сервере заведения. Раз в N секунд:
- пингует cloud-портал («я живой»)
- шлёт метрики (CPU, RAM, диск, статус сервисов)
- слушает команды из портала (рестарт сервиса, обновление, открыть туннель)
- стримит свежие логи

**Безопасность:**
- Каждый агент — со своим клиент-сертификатом (mTLS)
- Туннель открывается **только по запросу** и только на ограниченное время
- Все действия сервиса логируются в audit_log на стороне заведения
- Никакого «скрытого» доступа — владелец видит, кто и когда заходил

## 8. Поэтапный план реализации

### Этап 1. Каркас (2–3 недели)
- БД, миграции, базовые модели (меню, заказ, пользователь)
- POS-страница: список категорий → блюдо → корзина → оплата (без фискалки)
- Печать pre-bill в PDF
- Простой отчёт «выручка за день»

### Этап 2. Кухня и роутинг (1–2 недели)
- Привязка блюд к станциям приготовления
- KDS-экран (та же страница в kiosk-режиме)
- Статусы блюд: новое → в работе → готово → выдано

### Этап 3. Печать чеков и закрытие смены (1 неделя)
- Интеграция с ESC/POS термопринтером
- Внутренние X/Z-отчёты, открытие/закрытие смены
- Журнал операций

### Этап 4. Склад и ТТК (2–3 недели)
- Справочник ингредиентов и поставщиков
- Приёмка накладных
- ТТК и автосписание при продаже
- Инвентаризация и расхождения

### Этап 5. AI-слой и приложение закупщика (3–4 недели) — приоритет
- `ai-gateway` сервис с интеграцией Claude API
- Распознавание накладных по фото → черновик прихода
- Мобильное приложение закупщика (PWA), офлайн-режим
- Голосовой ввод позиций (Whisper)
- Матчер ингредиентов с обучением на подтверждениях
- Ежедневный AI-отчёт владельцу в Telegram

### Этап 6. Лояльность и доставка (опционально)
- Простая дисконтная программа по номеру телефона
- Webhook для приёма заказов с агрегаторов
- QR-меню со столика

### Этап 7. Облако и мульти-точка
- Демон выгрузки данных в облачную БД
- Веб-кабинет владельца с отчётами по двум кафе
- Бэкапы в S3
- Прогноз продаж и закупа по обоим заведениям

### Этап 8. Сервисное обслуживание
- `remote-agent` на сервере заведения
- Cloud Service Portal: дашборд, тикеты, метрики, удалённый доступ
- Механизм обновлений и rollback
- (Опционально) реестр оборудования кафе и графики ТО

## 9. Оценка сложности и затрат

| Параметр | Покупка R-Keeper / iiko / Square | Своя разработка | Odoo + кастом |
|---|---|---|---|
| Стартовые затраты | Лицензии + внедрение за точку | 0 за ПО, только ваше время | 0 за ПО, время на кастом |
| Срок запуска | 1–2 недели | Несколько месяцев | 1–2 месяца |
| Гибкость | Низкая | Максимальная | Высокая |
| Поддержка | Вендор / дилер | Только вы | Сообщество + вы |
| Зависимость от вендора | Полная | Нет | Низкая |
| AI-фичи из коробки | Почти нет | Полная свобода | Ограниченно |
| Сервисное обслуживание | Через дилера | Свой портал | Свой портал |

**Вывод:** для 1–2 кафе, если **есть инженер** — оправдано взять Odoo или Floreant и дописать; если инженера нет — купить готовый R-Keeper / iiko / Poster и не страдать. Своя разработка с нуля имеет смысл только при долгосрочном плане превратить её в продукт.

## 10. ИИ-возможности (ключевое требование)

Главное отличие самописной системы от R-Keeper/iiko — **возможность встроить LLM и vision-модели в любой бизнес-процесс**. Это превращает учётную систему в *ассистента*, а не просто формочки. Ниже — конкретные сценарии и архитектура.

### 10.1. Распознавание бумажных накладных (OCR + LLM)

**Задача:** поставщик привёз товар с бумажной накладной (или чеком, или ТОРГ-12). Кассир/завпрод фоткает её на телефон → через 5 секунд в системе появляется черновик приходной накладной с позициями, ценами и привязкой к ингредиентам в справочнике.

**Поток:**

```
Фото → S3/локальное хранилище
   ↓
Препроцессинг (выпрямление, кроп, контраст — OpenCV)
   ↓
OCR (Tesseract / PaddleOCR / Yandex Vision / Google Vision)
   ↓
LLM-парсер (Claude 4.6 / GPT) с инструкцией:
   "Извлеки таблицу позиций: наименование, кол-во, ед., цена, сумма.
    Верни JSON по схеме."
   ↓
Маппинг названий на справочник ингредиентов
   (нечёткое сравнение + LLM с few-shot из истории закупок)
   ↓
Черновик прихода в БД → менеджер подтверждает → постинг на склад
```

**Технические детали:**

- **Лучше всего работает мультимодальная LLM напрямую** (Claude с image input или GPT-4o). OCR-этап можно вообще пропустить — модель сама читает фото и возвращает структурированный JSON. Это даёт +20–30% точности на корявых рукописных накладных по сравнению с pipeline «OCR → LLM».
- **Структурированный вывод обязателен.** Через `tool_use` или JSON Schema — иначе придётся парсить свободный текст.
- **Обучаемый словарь синонимов.** «Помидоры красные» / «томаты св.» / «pomidor» — все мапятся на один ингредиент. Каждое подтверждение менеджера сохраняется как пример для будущего матчинга.
- **Confidence score.** Если уверенность < 90% — позиция помечается жёлтым, требует ручного подтверждения. Если > 95% — авто-привязка.
- **Хранение оригинала.** Фото накладной всегда лежит рядом с записью в БД — для аудита и налоговой.

### 10.2. Приложение для закупщика (рынок, наличный расчёт)

**Контекст:** каждое утро человек едет на оптовый рынок (Фуд-сити, оптовка), покупает овощи/мясо/рыбу за наличку, привозит на кухню. Бумажки — чеки, пометки в блокноте, иногда вообще ничего. Задача — превратить это в учёт без бюрократии.

**Сценарий использования (мобильное приложение):**

1. **Утром.** Шеф формирует «лист закупки» в системе на основе:
   - стоп-листа с прошлого вечера
   - текущих остатков ниже минимума
   - плана продаж (LLM прогнозирует продажи на день по истории + день недели + погода)
   - ручных правок шефа
2. **На рынке.** Закупщик видит на телефоне список: «Помидоры — 12 кг, бюджет 600 ₽/кг, до 7200 ₽».
   - Покупает позицию → жмёт галочку → **фоткает товар** (для контроля качества) и **фоткает чек/ценник**
   - LLM сразу распознаёт цену и вес → пишет фактическую сумму
   - Если цена выше плановой — алерт «перерасход 15%, подтвердить?»
3. **Голосовой ввод.** Если рук нет: «Купил картошку 20 кило по 35 рублей» → LLM парсит → запись в системе. (Whisper для распознавания речи + Claude для парсинга.)
4. **По возвращении.** На кухне приёмщик сверяет: вес по факту (взвешивает) vs по приложению. Расхождения автоматом фиксируются.
5. **Финансы.** Закупщик берёт под отчёт сумму X, в конце дня приложение показывает: куплено на Y, остаток Z, **фото всех чеков** для отчёта бухгалтеру. Кэш-репорт формируется автоматически.

**Что даёт ИИ конкретно тут:**

| Функция | Модель | Зачем |
|---|---|---|
| Распознавание чеков | Vision LLM | Превратить фото в строки прихода |
| Голосовой ввод | Whisper + LLM | Руки заняты — говоришь и работаешь |
| Прогноз закупа | LLM/классическая ML | «Сколько брать помидоров завтра» по истории |
| Контроль цен | LLM-агент | Сравнить с прошлой неделей, поднять алерт |
| Поиск замены | LLM | «Лосося нет — что заменить и в каких блюдах поменять стоп-лист» |
| Анализ фото товара | Vision | «Свежесть зелени», «целостность упаковки» (опционально) |

**Архитектура приложения закупщика:**

```
┌────────────────────────────┐
│ Mobile App (PWA / Flutter) │
│ - офлайн-первое            │
│ - локальная очередь        │
│ - фото в кэше              │
└──────────────┬─────────────┘
               │ (sync когда есть сеть)
               ▼
┌────────────────────────────┐
│ Backend API (FastAPI)      │
│ - /procurement/list        │
│ - /procurement/scan-receipt│
│ - /procurement/voice       │
└──────────────┬─────────────┘
               │
       ┌───────┴─────────┐
       ▼                 ▼
┌──────────────┐   ┌──────────────┐
│ AI-сервис    │   │ PostgreSQL   │
│ - Claude API │   │ - закупки    │
│ - Whisper    │   │ - чеки       │
│ - матчинг    │   │ - бюджеты    │
└──────────────┘   └──────────────┘
```

**Важно — офлайн-режим.** На рынке часто нет связи. Приложение должно:
- держать локальную копию листа закупки
- складывать фото и голос в локальную очередь
- синкаться, как только появилась сеть
- LLM-вызовы откладываются и батчатся — закупщик может сначала всё купить, а распознавание идёт в фоне после возврата

### 10.4. Архитектура AI-слоя в системе

Вынести в **отдельный сервис `ai-gateway`**, чтобы:

1. Не зависеть от вендора. Сегодня Claude, завтра локальная Llama — меняется только в одном месте.
2. Кэшировать ответы (одинаковые накладные приходят раз в неделю — можно дешевле).
3. Логировать все вызовы для аудита и улучшения промптов.
4. Считать стоимость по точкам/функциям.

```
┌──────────────────────────────────┐
│ ai-gateway                       │
│                                  │
│ POST /vision/parse-invoice       │
│ POST /vision/parse-receipt       │
│ POST /audio/transcribe           │
│ POST /llm/match-ingredient       │
│ POST /llm/forecast-sales         │
│ POST /llm/daily-summary          │
│                                  │
│ - prompt templates               │
│ - schema validation              │
│ - retry / fallback               │
│ - cost tracking                  │
│ - cache (Redis)                  │
└──────────┬───────────────────────┘
           │
   ┌───────┼────────┬─────────┐
   ▼       ▼        ▼         ▼
┌──────┐┌──────┐┌──────┐┌──────────┐
│Claude││ GPT  ││Local ││ Whisper  │
│ API  ││ API  ││ Llama││  API     │
└──────┘└──────┘└──────┘└──────────┘
```

**Модели по умолчанию:**
- Распознавание накладных, чеков, OCR-задачи: **Claude Opus 4.6** (мультимодальная, точнее всех на табличных и рукописных данных)
- Лёгкие задачи (матчинг, классификация, парсинг текста): **Claude Haiku 4.5** — дёшево и быстро
- Голос → текст: **Whisper** (OpenAI API или локально через `whisper.cpp`)
- Прогноз продаж: гибрид — Prophet/LightGBM для базовой модели + LLM для интерпретации и аномалий

**Промпт-кеширование** (важно для экономии): системные промпты с описанием справочника ингредиентов и схемы JSON — кэшируются. Реальная экономия до 90% на повторных вызовах.

### 10.5. Где это даёт реальную экономию

- **Закупщик:** 1–2 часа в день экономии на ручном вводе чеков → ~30 ч/мес
- **Завпрод/менеджер:** приходные накладные за минуты вместо часа
- **Шеф:** прогноз закупа точнее → меньше списаний просрочки (фудкост −2..5%)
- **Владелец:** ежедневный AI-отчёт с аномалиями → не нужно сидеть в дашбордах

Это **главное конкурентное преимущество** перед R-Keeper/iiko: они сидят на старой архитектуре, AI-фичи у них либо отсутствуют, либо приклеены сбоку. Новая система может строиться **AI-first**.
