# Модель разработки: мульти-агентная

## Роли агентов

### Архитектор (основной)
Ведёт общий контекст проекта. Отвечает за:
- ERD, миграции, общие сущности.
- API-контракты между модулями.
- Код-ревью PR от модульных агентов.
- Разрешение конфликтов на швах.
- Обновление документации в vault.

В Claude Code это основная сессия: я в этой роли.

### Модульные агенты (по одному на модуль)
Каждый запускается через инструмент Agent со своей спецификацией. Работают параллельно в изолированных worktree-ветках. Видят:
- Свой модуль в `code/backend/app/modules/<name>/` и соответствующий фронтенд.
- Свою спецификацию `03-modules/NN-<name>.md`.
- Общие сущности и контракты (read-only): `code/backend/app/core/`, `04-erd.md`.

Не видят и не трогают: чужие модули.

### Вспомогательные агенты
- **Explore** — быстрые запросы по кодовой базе при ревью.
- **Plan** — проектирование изменения перед имплементацией.
- **general-purpose** — задачи на стыке модулей.

## Процесс разработки модуля

1. **Интервью с PO**: архитектор записывает в `03-modules/NN.md` процесс, бизнес-правила, закрывает open questions.
2. **Проектирование**: архитектор расширяет ERD, заводит миграцию, пишет API-контракт модуля (OpenAPI stub).
3. **Делегирование**: архитектор запускает модульного агента через Agent tool с чётким промптом и ссылкой на спеку.
4. **Разработка агентом**: агент пишет backend-код модуля, миграции, тесты, фронтенд, коммитит в свою ветку.
5. **Ревью архитектором**: проверка на соответствие контрактам, архитектуре, стилю. Правки по ревью.
6. **Интеграционное тестирование**: общий e2e-тест — «продажа на POS списывает ингредиенты со склада».
7. **Пилот**: разворачиваем в реальной столовой, PO тестирует, фиксирует баги — они становятся следующими задачами агентов.

## Правила для модульных агентов (зашиваются в промпт)

1. **Ни одна строчка вне своей папки.** Общие сущности — только read.
2. **Все изменения БД — через Alembic-миграции**, не через ручной SQL.
3. **Каждый публичный API endpoint — документируется в OpenAPI** и покрывается тестом.
4. **Не писать бизнес-логику в контроллерах.** Разделение: `router.py` (HTTP) → `service.py` (бизнес) → `repository.py` (БД).
5. **Если нужна фича от другого модуля** — не лезть в его код, а попросить архитектора расширить контракт.
6. **Стиль**: ruff + mypy на backend, ESLint + Prettier на frontend. CI должен быть зелёный.

## Артефакты, которые всегда синхронизированы
- `03-modules/NN.md` — ТЗ
- `code/backend/app/modules/<name>/` — имплементация
- `code/backend/tests/modules/<name>/` — тесты
- OpenAPI schema на `/docs` — актуальное API

Если что-то из этого рассинхронизировано — это баг, разрешает архитектор.

## Как PO взаимодействует с системой
- Пишет в чат архитектору (Claude Code сессия) — словами, по одному модулю.
- Архитектор обновляет `03-modules/NN.md`, обсуждает открытые вопросы.
- Когда модуль описан — архитектор запускает разработку.
- PO не лезет в код, не делает ревью. Его зона — процесс, тестирование на пилоте, решения.
