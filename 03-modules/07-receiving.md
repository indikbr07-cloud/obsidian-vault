# Модуль 7. Приёмка товара

## Назначение
Оформить поступление товара от поставщика — оприходовать на склад сырья. Три канала ввода: электронный документ (ЭДО-УПД), OCR бумажной накладной и ручной ввод. Каждый канал даёт черновик документа «Приход», кладовщик проверяет и проводит.

## Пользователи
- Кладовщик (основной — принимает товар, проверяет)
- Менеджер (контроль, правка цен)

## Каналы ввода

### Канал 1. ЭДО (УПД-XML)
- Поставщик присылает УПД через оператора ЭДО (Диадок / СБИС / Контур).
- В MVP — кладовщик скачивает XML от оператора и загружает в систему.
- Система парсит XML, создаёт черновик прихода с позициями.
- **Ключевая фича — матчинг номенклатуры**: у поставщика «Молоко 3.2% Простоквашино 1л», у нас в справочнике «Молоко 1л». Нужен словарь соответствий `поставщик × артикул → наша карточка`. При первой загрузке — кладовщик сопоставляет вручную, дальше автоматом.

### Канал 2. OCR бумажной накладной
- Кладовщик фотографирует накладную телефоном, загружает в систему.
- Система отправляет изображение в Yandex Vision OCR.
- Распознаёт табличные данные: позиция, количество, цена, сумма.
- Создаёт черновик прихода.
- Кладовщик проверяет и правит перед проведением.

### Канал 3. Ручной ввод
- Кладовщик создаёт документ с нуля: выбирает поставщика, добавляет позиции.

## Экраны
- Входящие накладные (список): статус (черновик / проведён), поставщик, сумма.
- Карточка накладной: редактирование, загрузка XML/фото, матчинг позиций.
- Словарь соответствий «артикул поставщика → наша карточка».

## Бизнес-правила
- Черновик нельзя провести, если есть нематченные позиции (или можно с пометкой «несопоставлено», уточнить).
- При проведении — остаток сырья на складе увеличивается, запоминается закупочная цена, пересчитывается себестоимость зависимых блюд.
- Ценовая история: по каждому ингредиенту храним все закупочные цены с датами.

## API
- `POST /api/receiving/upload-xml`
- `POST /api/receiving/upload-photo` (запускает OCR асинхронно)
- CRUD `/api/receiving/docs`
- CRUD `/api/receiving/supplier-mapping`
